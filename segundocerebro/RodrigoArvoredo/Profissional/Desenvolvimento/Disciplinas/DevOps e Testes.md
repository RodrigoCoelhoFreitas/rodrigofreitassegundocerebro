# DevOps e Testes

Ramificação de [[Disciplinas]]. Cada um dos 3 projetos tem uma estratégia de deploy diferente.

## Estado do ecossistema (2026)

- **Docker** segue como a resposta padrão pra tudo que não é função serverless de vida curta: runtime com dependências binárias (browser headless, client de banco compilado, fontes), processo long-running numa porta fixa, cron/worker. Prática consolidada: imagens `-slim`/multi-stage, instalar só o necessário via `apt` com repositório extra quando o pacote da distro base está desatualizado.
- **Easypanel** é um painel self-hosted de PaaS (tipo Heroku/Coolify/Dokploy): instala numa VPS própria (Hetzner, Contabo, etc.), builda a partir de Dockerfile/docker-compose ou Nixpacks, dá domínio + certificado TLS automático, e expõe um botão de deploy manual ou webhook de auto-deploy por branch — sem abstrair o container, ao contrário de Vercel/Railway. Diferencial real em 2026: UI mais polida que a concorrência open-source, mas com modelo misto — parte dos recursos avançados (backups automáticos, múltiplos usuários/times) fica atrás de um Pro pago, enquanto Coolify e Dokploy entregam tudo de graça por serem 100% open-source. Faz sentido trocar Vercel/Railway por Easypanel quando o custo é fixo (uma VPS por um preço fixo vs. cobrança por uso) e quando o workload não é "function serverless" — é container que precisa rodar sempre ligado, com binário pesado (Chromium, certificados de banco) ou processo próprio numa porta.
- **Vercel** continua a plataforma de referência pra Next.js: zero-config (detecta o framework no import, build command e output inferidos), preview deployment automático por PR/branch, e desde abril/2025 o **Fluid Compute** é o modelo padrão pra projetos novos — funções deixam de ser "uma invocação = uma instância isolada" e passam a compartilhar instância entre invocações concorrentes, cortando cold start e custo (cobra CPU ativa, não o tempo todo da invocação). `waitUntil` virou o padrão pra trabalho em background pós-resposta (log, analytics) sem segurar a resposta ao usuário. Contrapartida: o runtime de função da Vercel ainda tem restrições que não existem rodando Node puro (ex.: APIs globais como `SharedArrayBuffer` se comportam diferente e exigem tratamento explícito em SDKs que assumem Node "normal", como o AWS SDK).
- **Playwright** consolidou a posição de framework padrão pra E2E, ultrapassando o Cypress em adoção por uma margem grande (ordem de 5x em downloads semanais no npm em 2026). Diferença estrutural: Playwright roda fora do processo da página, controlando o browser via protocolo (WebSocket), o que permite múltiplas abas/origins/contexts na mesma sessão e suporte nativo a três engines (Chromium, Firefox, WebKit) — Cypress roda dentro do loop da própria aplicação, o que dá um debugging por "time travel" muito bom mas trava em um browser por teste e não cobre múltiplas origins de verdade. Outra diferença prática: paralelização no Playwright é nativa e gratuita (sharding via CLI/CI); no Cypress, paralelização real, gravação e analytics ficam atrás do Cypress Cloud, que é pago. Isso faz do Playwright a escolha default pra suites que precisam crescer além de algumas dezenas de testes sem depender de um SaaS de terceiros.

## Quando isso importa

- No **[[1060crm]]**, o deploy é na Vercel — Next.js direto na plataforma que o suporta nativamente. Reflexo concreto disso no código: o uso do AWS SDK precisa de tratamento específico pra `SharedArrayBuffer`, porque o runtime de função da Vercel não se comporta como um Node "normal" nesse ponto — sintoma direto da contrapartida citada acima sobre restrições do runtime serverless.
- No **[[NapShift Backend]]**, o deploy é Docker + Easypanel, manual (sem auto-deploy — precisa clicar em "Implantar" depois do push). O `Dockerfile` parte de `node:22-slim`, instala Chromium + fontes (pra geração de PDF/renderização) e `postgresql-client-17` via repositório PGDG — necessário porque o Debian Bookworm só traz PostgreSQL 15 no repo padrão, e o client precisa bater com a versão 17 do banco em produção. Build compila TS via `npx tsc` e roda `node dist/index.js` fixo na porta 3200 — perfil clássico de "container que precisa ficar ligado com binário pesado", exatamente o caso de uso onde Easypanel faz mais sentido que Vercel. Existem dois serviços separados no painel: produção (`api.napshift.com`, branch `main`) e homolog (`homolog-api.napshift.com`, branch `homolog`). Regra de trabalho: partir sempre da branch `homolog` — mas há uma exceção temporária em vigor, com o Rodrigo pedindo pra trabalhar a partir da `main` por enquanto.
- No **[[NapShift Web]]**, o deploy é Vercel com auto-deploy por branch (`main` → produção, `homolog` → homologação) — o caminho "padrão" que a plataforma foi feita pra suportar, sem fricção de container. Os testes E2E rodam em Playwright, com 3 projetos de teste configurados: `setup` (faz a autenticação e persiste o estado), `public` (roda sem auth) e `authenticated` (depende do `setup` rodar antes). Há fixtures customizadas (ex.: `clienteTest`) pra injetar contexto de teste sem repetir setup em cada spec. Estado atual: 58/58 testes passando, organizados 1:1 com a árvore de rotas (`tests/adm/*.spec.ts`, `tests/cliente/*.spec.ts` etc.) — a estrutura de pastas dos testes espelha a estrutura de páginas do App Router, não uma divisão arbitrária por "feature".
- O **NapShift Backend** também tem suite de testes, mas não usa Playwright nem nenhum framework externo de teste: são 239 testes rodando no test runner **nativo do Node** (`node --test`) + `tsx` pra TS direto, divididos em `tests/unit/` e `tests/integration/` — a integração usa a flag experimental `--experimental-test-module-mocks` pra poder mockar módulos ESM nos testes de integração, algo que o runner nativo historicamente não suportava bem antes dessa flag existir.

## Versionamento e fluxo de branches do NapShift (desde 2026-09-15)
Vale pros dois repos ([[NapShift Backend]] e [[NapShift Web]]), que são um produto só. Documento canônico: `docs/VERSIONAMENTO.md` no backend.
- **`homolog`** é integração e staging (default do GitHub). **Ninguém commita direto nela** (desde 2026-09-22, sessão com o Claude incluída): todo trabalho abre uma branch `feat/`, `fix/`, `chore/` ou `docs/` saindo de `homolog` e volta por merge com squash.
- **`main` é produção** e só recebe fast-forward de `homolog` pelo `npm run release -- X.Y.Z`, que roda a checagem (typecheck + testes no backend; `tsc` + lint no Web), faz o bump, dá o push com `RELEASE=1` e cria tag `vX.Y.Z` + branch `release/vX.Y.Z` no mesmo commit. Hotfix sai de `main` com `--hotfix`.
- **O GitHub não protege nada** (repos privados em conta Free não têm branch protection). A defesa é o hook `.githooks/pre-push`, que bloqueia push em `main` sem `RELEASE=1` e push non-fast-forward em `homolog`. **Ativar uma vez por clone:** `git config core.hooksPath .githooks` — feito na máquina do Rodrigo em 2026-09-29 e testado.
- Versões até aqui: savepoints antigos renumerados pra `0.x.y`; `v1.0.0` (2026-09-15), `v1.1.0` (2026-09-24), `v1.2.0` (2026-09-25).
- Deploy do backend é por hook do Easypanel (push não dispara sozinho); o Web sobe pela Vercel a partir de `main` (produção) e `homolog` (`homolog.napshift.com`, atrás de Vercel Authentication). Conferir o backend sempre pelo `gitSha` do `/health`.
- **Homolog não é descartável:** o banco tem dado real de cliente (restaurado da produção) e a Evolution (WhatsApp) é compartilhada com produção. Roda com `PIPELINE_ENABLED=false` e uma instância de WhatsApp inexistente de propósito; não existe modo de simulação.
- **Migrations:** geradas por `drizzle-kit generate`; o Eduardo aplica o SQL no DBeaver (`npm run db:sql` imprime o DDL + registro no journal). Várias de uma vez = um arquivo só, em transação.

**Atualização dos números (2026-09-29):** a suíte do backend passou de 239 pra ~1100 testes, ainda 100% mockada (nenhum executa SQL real — lacuna registrada no backlog). O Playwright do Web segue como estava; o lint do Web tem 191 erros antigos, e por isso as releases do Web saem com `--sem-testes`.

## Infraestrutura real (confirmado pelo Rodrigo, 2026-07-08) — trabalho em aberto
- Os projetos (pelo menos [[1060crm]] e [[NapShift Web]]) já estão configurados pra deploy automático via Vercel a partir de push no git — **mas ainda precisam de ajuste/organização**, não está tudo redondo.
- O **Easypanel roda numa VPS da Hostinger** — e não serve só pra hospedar o container do [[NapShift Backend]]: é lá que ficam **os bancos de dados e as APIs** do ecossistema todo. Também precisa de organização — tarefa pendente explícita, não só o container do backend.
- Ou seja: existe trabalho real de DevOps pendente nos dois lados (Vercel e Easypanel/Hostinger), não é só documentação — vale perguntar o estado atual antes de assumir que algo já está automatizado/organizado.
