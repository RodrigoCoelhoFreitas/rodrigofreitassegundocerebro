# Storage e Renderização

Ramificação de [[Disciplinas]]. Cloudflare R2 guarda os assets dos 3 projetos; Puppeteer é o motor que transforma template HTML em imagem de post pronta pra publicar.

## Estado do ecossistema (2026)

- **Cloudflare R2** manteve a proposta original (S3-compatible, zero fee de egress mesmo via API S3, Workers ou domínio `r2.dev`) e passou 2026 se reposicionando de "storage barato" para "plataforma de dados": R2 Data Catalog e R2 SQL chegaram pra consultar dados direto no bucket, sem mover objeto. Pricing segue simples ($0,015/GB de armazenamento + operações, egress $0), e a lacuna de egress contra S3/GCS continua sendo o motivo prático de escolha — ordens de grandeza mais barato em cargas de mídia/CDN-origin. Compatibilidade S3 real (mesmo SDK, mesmos verbos) é o que permite trocar de provider sem reescrever client code — exatamente o que sustenta o hot-swap do NapShift Backend abaixo.
- **Puppeteer segue sendo a escolha pragmática para o caso específico "HTML→imagem em lote, um engine só (Chromium), sem necessidade de cross-browser"** — API mais enxuta e overhead menor que Playwright pra essa tarefa fechada. Playwright é o default geral de 2026 pra automação/E2E (Firefox + WebKit + Chromium, trace viewer, auto-wait), mas isso é peso desnecessário quando o output é sempre um PNG gerado no mesmo engine determinístico; escolher Puppeteer aqui é coerente com o recorte, não uma escolha datada. Em ambos, o custo real de produção não é a lib, é a infra ao redor: pooling de browser (200-500MB RAM por instância), flags de sandbox em Docker, updates de Chromium, retries — daí o padrão de reaproveitar um singleton de browser entre chamadas em vez de abrir/fechar processo a cada render.
- **Renderizar HTML não-confiável em browser headless é vetor de SSRF reconhecido e subestimado** — o motor (Puppeteer, Playwright, wkhtmltopdf) busca automaticamente qualquer recurso referenciado no HTML (`<img>`, `<iframe>`, `<link>`, CSS `url()`), então um template com placeholder mal-saneado ou conteúdo injetado pode forçar o servidor a fazer requests pra IPs internos, metadata endpoint de cloud (`169.254.169.254`) ou serviços atrás do firewall — o browser vira proxy involuntário dentro da rede do servidor de renderização. Mitigação padrão de 2026 continua sendo allowlist de host na camada de interceptação de request (não sanitização de string) somada a desabilitar JS quando o template é estático — JS ligado abre canal adicional (`fetch`/XHR) que escapa de qualquer allowlist de recurso estático da página.

## Quando isso importa

- No **[[1060crm]]**, R2 guarda imagens de referência/preview de lead: upload via AWS SDK S3 client + `sharp` fazendo resize (1600px) e conversão pra WebP antes de gravar. Bug real corrigido em múltiplos commits — buffers do runtime Vercel às vezes chegam como `SharedArrayBuffer`, tipo que o AWS SDK/`@smithy` recusa explicitamente; `r2.ts` precisa recopiar pra um `ArrayBuffer` comum antes do `PutObject`. R2/Resend vieram herdados do template do site institucional; só R2 pra imagem de lead é usado de fato no v1.
- No **[[NapShift Backend]]**, storage é dual: R2 primário, Supabase Storage como fallback hot-standby, com hot-swap automático via `storage-providers/factory.ts` — só viável porque os dois falam o mesmo protocolo S3-compatible. O gatilho não é genérico: `services/instagram.ts` detecta especificamente o erro `9004`/subcode `2207052` que a Graph API do Instagram devolve quando não consegue baixar a `image_url` fornecida (bloqueio de fingerprint do storage primário, observado desde 2026-04-22). Ao detectar, baixa do provider atual e regrava no fallback **com o mesmo nome de objeto** (idempotente), cap de 1 retry — não fica alternando provider indefinidamente.
- **Renderização** (`services/renderer.ts`) usa Puppeteer com um browser Chromium **singleton** reaproveitado entre chamadas (evita cold-start de 200-500MB por render), JS desabilitado na página (templates são estáticos, sem necessidade de runtime), e — a defesa de SSRF descrita acima aplicada de verdade — interceptação de request bloqueando qualquer host fora de uma allowlist (fonts do Google + o host de R2/Supabase configurado). Placeholders `{{variavel}}` são substituídos por regex (viram string vazia se ausentes, nunca "undefined" visível na imagem), `*texto*` vira destaque visual também via regex. PNG final passa por validação de tamanho mínimo (10KB) como heurística barata de "página renderizou em branco".
- **Templates HTML** ficam versionados em `templates/` no repo (genéricos + variantes por cliente, ex. `templates/clientes/1060-brand/`) — mas isso é só referência de dev. Os templates que realmente rodam em produção vivem no banco (`agencia_referencias`, tipo `template_*`), armazenados como objeto no R2 e carregados em runtime; os arquivos do repo podem estar desatualizados frente ao que está de fato publicado.
