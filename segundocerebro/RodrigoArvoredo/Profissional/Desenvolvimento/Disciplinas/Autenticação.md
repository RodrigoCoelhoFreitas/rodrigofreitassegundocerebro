# Autenticação

Ramificação de [[Disciplinas]]. Cada um dos 3 projetos resolve autenticação de um jeito diferente.

## Estado do ecossistema (2026)

- **Auth.js (ex-NextAuth) mudou de mãos em set/2025**: Balazs Orban (mantenedor principal) saiu em jan/2025, o v5 ficou travado em beta desde out/2023, e o time do Better Auth assumiu a manutenção — anúncio "Auth.js is now part of Better Auth". Hoje Auth.js está oficialmente em **modo manutenção**: só patch de segurança, zero feature nova. Quem já usa continua funcionando sem ruptura, mas a recomendação pra projeto novo é Better Auth, exceto quando falta exatamente o que Better Auth ainda não cobre bem: **sessão 100% stateless (JWT) sem depender de banco** — que é justamente o caso do 1060crm.
- **JWT vs database session** continua a decisão central de qualquer setup Auth.js/Better Auth: `session: { strategy: "database" }` exige ida ao banco a cada request (revogação imediata, mas não roda em edge); `strategy: "jwt"` verifica a sessão com `jose` (Web Crypto API) sem tocar banco — roda em edge/middleware, mas revogação de sessão não é imediata (o token continua "válido" até expirar, a menos que a app releia autorização do banco por fora do JWT).
- **Split config (`auth.config.ts` + `auth.ts`)** é o padrão que o próprio Auth.js empurra desde o v5 e que virou obrigatório de fato com Next.js rodando middleware em edge runtime por padrão: o arquivo edge-safe carrega só providers/callbacks/`pages`, sem adapter; o arquivo Node completo importa esse config, adiciona o adapter (Prisma/Drizzle/etc.) e força a strategy. Sem essa separação, middleware em edge quebra tentando abrir conexão de banco.
- **Multi-tenant/multi-portal com JWT**: o padrão de 2026 não mudou muito na essência — claims de tenant/workspace/portal embutidas no token, filtragem de query por esse claim no backend — mas o consenso deslocou pra tratar o JWT como **prova de identidade, não de autorização**: middleware/edge só decide "tem token, deixa passar"; quem decide permissão fina (role, tenant certo, ativo/inativo) é sempre uma camada que releva estado a partir de uma fonte de verdade viva (banco), não do payload assinado. Token de acesso curto + refresh token separado é o padrão recomendado para apps que reautorizam frequentemente; JWT de vida longa sem refresh é aceito como trade-off consciente quando o app já releva autorização por fora.
- **Google OAuth**: consent screen antigo virou "Google Auth Platform" (abas Branding/Audience/Clients). Scopes sensíveis/restritos seguem exigindo verificação (2-6 semanas, CASA Tier 2 pra restritos); `openid email profile` (o caso de login básico) não entra nessa fila. Regra reforçada em 2026: telas de consentimento e uso de dados para treino de IA exigem consentimento afirmativo explícito documentado.
- **Facebook Login for Business** virou (30/jun/2026) a via preferencial pra tech providers que integram com ferramentas de negócio da Meta; `email`/`public_profile` seguem auto-concedidas, mas todo app precisa declarar ao menos mais uma permissão suportada. App Review segue sendo o gargalo real: permissões aprovadas ficam disponíveis pra qualquer usuário do app; permissões não aprovadas só funcionam pra quem tem role dentro do próprio app Meta (ou seja, só o time interno consegue testar até a submissão passar).
- **Apple Sign In** segue como o provider mais rígido em termos de exigência de plataforma (obrigatório em apps iOS que oferecem login social) e o de schema mais simples de aderir depois — é o motivo de times prepararem a tabela de OAuth genérica mesmo sem implementar o fluxo ainda.

## Quando isso importa

- No **[[1060crm]]**: `next-auth@5.0.0-beta.31` rodando em cima do Next.js 16.2.2 — literalmente o cenário "modo manutenção, mas é o único que resolve stateless JWT sem banco" descrito acima. Só provider Google. `auth.config.ts` é edge-safe (sem adapter, sem DB) e roda no proxy/middleware; `auth.ts` é a versão Node completa com `DrizzleAdapter` e a checagem de allowlist (tabela `app_users`, `ativo = true`) dentro do callback `signIn` — quem não está lá nem consegue criar sessão. Sessão é **JWT, não database session**, escolha deliberada para o middleware validar sem tocar o banco. Mas o JWT nunca é fonte de autorização: `getSessionUser()` (`src/lib/session.ts`) relê `role` e `ativo` do banco a cada request — desativar um usuário em `app_users` tem efeito imediato mesmo com um JWT antigo ainda "válido" circulando, porque a allowlist bloqueia no login e a releitura bloqueia em todo request subsequente.
- No **[[NapShift Backend]]**: auth multi-camada — senha própria (bcrypt) e Google OAuth (`src/routes/oauth.ts`) hoje; schema já pronto para Apple/Facebook via `agencia_usuario_oauth` (tabela genérica de vínculo, não implementação). O fluxo Google tem dois modos que compartilham o mesmo `redirect_uri`: `mode=login` (público, gera JWT direto) e `mode=link` (autenticado, vincula conta OAuth a um usuário já logado), diferenciados por um `state` CSRF com TTL de 10 min guardado em memória. **App Review da Meta é frente de trabalho ativa e incompleta** — há documentação própria disso no projeto (`docs/META-APP-REVIEW-SUBMISSIONS.md`, `.claude/memory/meta-app-review.md`), porque a submissão de permissões é feita em lotes e cada lote trava features novas até aprovar.
- No **[[NapShift Web]]**: autenticação **dual-portal** via dois cookies separados — `napshift-token` (JWT puro, sem refresh token, sem localStorage, `SameSite=Lax`, 7 dias) e `napshift-portal` (`adm` | `cliente`). `isADM`/`isGerente`/`isCliente` são derivados só de `user.tipo` que vem do backend, não de nada decodificado no frontend. Troca de workspace reemite um JWT novo com claim `wsa` (workspace ativo) sem logout/reload — o frontend só troca o cookie. O `middleware.ts` (`src/middleware.ts`) é o exemplo prático do princípio "JWT é identidade, não autorização" levado ao extremo, inclusive como gap conhecido: ele só checa **presença** do cookie `napshift-token`, nunca decodifica nem valida o JWT, e não confere se o `napshift-portal` bate com a rota (`/adm/*` vs `/cliente/*`) sendo acessada. A proteção real — token válido, portal certo, permissão certa — fica inteiramente a cargo do backend rejeitando o JWT errado nas rotas protegidas; o middleware do frontend é só UX de redirect, não linha de defesa.
