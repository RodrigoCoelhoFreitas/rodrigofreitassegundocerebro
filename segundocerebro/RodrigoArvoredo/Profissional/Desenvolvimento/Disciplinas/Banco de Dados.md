# Banco de Dados

Ramificação de [[Disciplinas]]. PostgreSQL + Drizzle ORM são usados nos 3 projetos, mas com filosofias diferentes de schema.

## Estado do ecossistema (2026)

- **PostgreSQL** segue em ritmo anual: 17 é a linha estável mais usada em produção (patches como 17.6), 18 já rodando em muita gente, e a 19 entrou em beta em junho/2026 — destaque para merge/split de partições nativamente, mais casos de partition pruning pelo planner, `default_toast_compression` passando a `lz4` por padrão e JIT desligado por padrão (histórico de mais prejuízo que ganho em cargas OLTP comuns).
- **RLS (Row Level Security)** amadureceu como a forma padrão de multi-tenancy sem schema-per-tenant: políticas por tabela, ativadas com `ENABLE ROW LEVEL SECURITY`, aplicadas antes de qualquer query do app rodar — inclusive para service roles anônimos/JWT-based. Correções recentes de segurança fecharam brechas onde RLS não cobria estatísticas em hierarquias de partição/herança.
- **JSONB** continua sendo o meio-termo padrão entre schema rígido e documento livre — indexável (GIN), agora com funções como `jsonb_strip_nulls` marcadas `immutable` (usáveis em índice), mas sem nada de "schema dentro do JSONB": tipagem e remapeamento de chaves são responsabilidade da aplicação, não do banco nem do ORM.
- **Drizzle ORM** consolidou-se como a alternativa "SQL-like" ao Prisma: wrapper fino sobre SQL, ~7KB gzip, zero dependência de runtime pesado, tipos inferidos direto da query (sem geração de client separado). Ganhou tração forte em edge/serverless (Cloudflare Workers, Vercel Edge, Lambda) justamente por não carregar engine binária.
- **Prisma**, em resposta, reescreveu o query engine (Prisma 7): saiu o engine Rust de ~14MB, entrou um Query Compiler TS/WASM de ~1.6MB (600KB gzip) — reduzindo a distância de performance/bundle que era a maior crítica ao Prisma. Ainda assim, Prisma continua "schema-first" com camada de abstração mais alta; Drizzle continua "code-first", mais perto do SQL cru.
- **Drizzle Kit — três fluxos distintos, não intercambiáveis**: `generate` cria arquivos `.sql` de migration a partir do diff do `schema.ts` (revisáveis, versionáveis, dá pra editar à mão antes de aplicar); `push` sincroniza o schema direto no banco sem gerar arquivo — rápido para prototipagem, mas gera drift não documentado se usado em produção; `pull` faz o caminho inverso, introspecciona um banco existente e gera o `schema.ts` a partir dele. `migrate` aplica os arquivos gerados pelo `generate`. Escolher entre eles é uma decisão de "quem manda": o `schema.ts` ou o banco.

## Quando isso importa

- No **[[1060crm]]**, o Drizzle é a fonte de verdade: `schema.ts` escrito à mão, migrations geradas via `drizzle-kit generate` e aplicadas por um script próprio (`db:migrate`) — fluxo "code-first" clássico. Tabelas de domínio: `app_users`, `leads`, `lead_fit`, `opportunities`, `activities`, `lead_images`, mais as tabelas padrão do Auth.js (contas, sessões, tokens). Duas armadilhas recorrentes: `db.execute` do Drizzle não coage tipo nenhum — todo resultado de `sql` cru volta como `unknown`/tipagem genérica e precisa cast manual; e `inArray` com array vazio gera SQL inválido (`IN ()`), então todo call site precisa guard antes de montar a query.
- No **[[NapShift Backend]]**, é o inverso exato: o Postgres é a fonte de verdade, e o `schema.ts` (~38KB, 27 tabelas, prefixos `agencia_`/`sdr_`) é gerado via `drizzle-kit pull` — introspecção, não autoria. Migrations vivem como `.sql` manuais em `drizzle/*.sql`, aplicadas via DBeaver direto no banco e só depois re-introspectadas para atualizar o `schema.ts` — o Drizzle Kit nunca gerencia essas migrations diretamente. Isso produz o bug recorrente do projeto: campos dentro de colunas `jsonb` ficam em snake_case (contrato HTTP real) enquanto o `schema.ts` só remapeia nome de *coluna* (camelCase ↔ snake_case), nunca chaves *dentro* de um JSONB — então o TS mente sobre o shape do JSON e cada leitura/escrita de campo JSONB precisa checagem manual do contrato real. Regra dura: nunca fazer `JSON.stringify` antes de gravar em coluna `jsonb` — o driver `pg` já serializa, e serializar duas vezes grava uma string escapada dentro do JSONB. RLS está ativo em parte das tabelas (ex.: `agencia_conhecimento`), bloqueando acesso anônimo — motivo comum de "funciona local, dá vazio em prod" quando falta o JWT/role certo na conexão. A migração 046 foi o divisor de águas do schema: eliminou `agencia_clientes` e `agencia_configuracoes`, fundindo tudo em `usuarios` e `workspaces`.
- No **[[NapShift Web]]** (frontend) não há acesso direto a banco — tudo passa por REST contra o NapShift Backend, então nenhuma das duas filosofias acima se aplica ali; a única "verdade" visível no frontend é o contrato HTTP (que é exatamente onde os bugs de camelCase/snake_case do backend vazam para fora).
