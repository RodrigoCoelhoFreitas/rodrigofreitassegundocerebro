# 1060crm

Ramificação de [[Rodrigo Coelho Freitas]]. Repositório: `github.com/1060brand/1060crm`; nesta máquina em `C:\Users\Gamer\Documents\projetos\1060crm` (clonado em 2026-11-10; na máquina antiga era `c:\Users\Dell\Documents\projetos\1060crm`).

## Conceito de negócio
CRM interno da **1060 Brand**, agência que vende múltiplas frentes de produto (sites, [[NapShift Backend|NapShift]], branding, marketing, SDR/prospecção) para pequenos negócios locais brasileiros. Sistema fechado, acesso só por allowlist — não é multi-tenant, não tem cadastro público.

Dois papéis: **admin** (visão total) e **vendedor** (só vê o que lhe foi atribuído).

Modelo central: **`lead` (contato) vs. `opportunity` (deal)**. Um lead é a identidade estável de um contato prospectado — nunca é apagado. Cada frente de produto trabalhada nesse lead vira uma `opportunity` com pipeline de status próprio. Hoje só a frente **site** tem UI de pipeline ativa.

Processo real de negócio: prospecção via **scraping** (GPT-assisted) em massa por nicho, importação via CSV com dedupe, e auditoria/higienização contínua da base (o scraping alucina contatos falsos — pipeline dedicada via Apify para checar Instagram real vs. inexistente).

## Stack técnica
Next.js 16 (App Router) + React 19 + TypeScript · Auth.js v5 beta (Google, allowlist, sessão JWT) · Drizzle ORM + Postgres · Zod 4 + react-hook-form · Tailwind CSS 4 · Recharts (dashboards) · AWS SDK S3 client → Cloudflare R2 (imagens) + sharp · lucide-react.

Scripts principais: `db:migrate`, `db:seed-users` (allowlist), `import:leads`, `leads:export`/`leads:apply` (enriquecimento).

## Modelo de dados (essência)
- `app_users` — allowlist (role admin/vendedor).
- `leads` — contato estável (whatsapp/instagram/email únicos, parcial ignorando null); `archived_at` soft delete só admin.
- `lead_fit` — aderência A/B/C por (lead, produto).
- `opportunities` — a deal (lead, produto) única ativa; `owner_id` = vendedor atribuído; `plano`/`valor`/`proximo_passo`/`motivo`.
- `activities` — timeline append-only por lead (ligação, whatsapp, instagram, email, reunião, nota, mudança de status automática).
- `lead_images` — referências e previews de site no R2.

## Funcionalidades
Login Google com revogação imediata de acesso · listagem de leads com filtros por role · CRUD de lead com defesa anti-duplicata em 3 camadas · pipeline de deal por produto (lançar, reatribuir, editar, registrar contato, Ganho/Perdido/Gelado) · dashboard do vendedor (agenda por urgência) · dashboard admin (comparativo entre vendedores, drill-down) · upload/gestão de imagens (R2 + sharp) · modal de playbook de vendas · importação de planilhas + enriquecimento web · auditoria de leads via Apify.

## Gotchas e convenções
- Fuso **America/Sao_Paulo** tratado com cuidado extremo em queries e lembretes (ancorado a meio-dia para não "cair um dia antes").
- Buffers do runtime Vercel podem vir como `SharedArrayBuffer`, que o AWS SDK recusa — `r2.ts` recopia para `ArrayBuffer` comum.
- `db.execute` do Drizzle não coage tipo — resultados de `sql` cru precisam cast manual.
- `inArray` do Drizzle com lista vazia gera SQL inválido — helper `inArrayIds` protege.
- **Lição de ouro da auditoria de Instagram**: HTTP 429 (rate limit) não é sinal confiável de "perfil morto" — só 404 explícito conta. Um bug já quase apagou ~57 negócios reais por confundir os dois.
- `lib/crm.ts` é fonte única de verdade de domínio (produtos, papéis, pipelines), deliberadamente edge/client-safe (sem DB).
- R2/Resend estão nas dependências (herdados do template do site institucional) mas não usados de fato no v1, exceto R2 para imagens de lead.
- `PLANO_VALORES` (Essencial/Profissional/Premium) espelha os preços reais dos termos comerciais da 1060 Brand — ver [[Produto Sites]] em [[Vendas]] pro documento formal completo (planos, comissão do vendedor, prazos, cancelamento).

## Implementação em profundidade (`src/app/painel/actions.ts` e afins)

**Matriz de permissão real** (checada por action, não centralizada num middleware):
- `criarLead`: qualquer usuário; se quem cria é **vendedor**, o sistema já cria automaticamente uma `opportunities` de produto "site" com ele como dono — vendedor "nasce dono" da deal de Site ao cadastrar. Admin que cria lead não ganha deal nenhuma.
- `atualizarLead`: admin sempre; vendedor só se tiver alguma opportunity no lead (qualquer produto).
- `arquivarLead`, `lancarDeal`, `reatribuirDeal`, `excluirOportunidade`, `excluirAtividade`: **admin only**. Vendedor nunca arquiva lead, nunca lança/reatribui/exclui deal, nunca apaga atividade — só encerra via pipeline (Ganho/Perdido/Gelado), pra não perder histórico.
- `atualizarDeal`, `registrarContato`: admin sempre; vendedor só se for dono da opportunity.

**Anti-duplicata em 3 camadas** (não é só um unique index):
1. Pré-insert: `acharLeadDuplicado` monta OR sobre whatsapp/instagram/email preenchidos e busca match antes de gravar.
2. Mensagem diferenciada por role: admin recebe nome + id do lead existente (pode linkar direto); vendedor recebe "você já tem esse contato" se a duplicata for dele, ou mensagem propositalmente vaga ("fale com o admin") se for de outro vendedor — **não vaza a carteira alheia**.
3. Defesa de corrida (TOCTOU): 3 `uniqueIndex` parciais no banco (ignoram null) pegam duas inserções simultâneas que passaram pela camada 1 ao mesmo tempo; o catch intercepta `code 23505` do Postgres e devolve mensagem amigável em vez de erro 500.

**Mudança de status não é um evento separado**: ao registrar contato com `novoStatus`, o sistema valida contra os stages do produto, atualiza a opportunity (`ganhoEm`/`motivo` conforme o caso) e grava a activity manual **com o campo `status` preenchido** — não existe uma activity de `tipo: "mudanca_status"` disparada à parte; esse valor do enum é usado só para *excluir* essas linhas de cálculos de esforço no dashboard de vendedores. Toda mudança de status para "ganho" recalcula `leads.isCliente` reagregando as opportunities do lead.

**Escopo por role na listagem** (`leads-admin.ts`): vendedor só vê leads onde tem alguma opportunity (`EXISTS` correlacionado por `owner_id`). Mais sutil: os filtros de "Frente"/"Classe" mudam de **semântica** entre roles — pra admin miram a aderência passiva (`lead_fit`); pra vendedor, miram a frente/aderência **da deal que ele possui**, não a melhor aderência do lead. Mesmo lead pode aparecer com classificações diferentes pra admin vs. pra cada vendedor.

**Revogação de acesso imediata** (`session.ts`): a sessão Auth.js só fornece o e-mail; role e `ativo` são **relidos do banco a cada request**. Desativar alguém em `app_users` corta o acesso no próximo clique, sem esperar expirar token ou logout — o JWT nunca é fonte de autorização, só de identidade.

**Métricas do dashboard de vendedores** (`vendedores-admin.ts`): núcleo é um reducer puro em memória sobre linhas já agregadas no banco (`owner × rating × status`). Vários cálculos exigem SQL cru com CTEs porque envolvem subquery correlacionada dentro de agregação (ex: "primeiro contato por lead" comparado ao dia corrente) ou `at time zone 'America/Sao_Paulo'` — não representável no query builder do Drizzle. "Abordados hoje" e "primeiro contato" ignoram deliberadamente o filtro de período (`since`), senão um lead antigo "renasceria" como contato novo ao trocar o range do dashboard. Ciclo médio de venda = `avg(epoch(ganhoEm - createdAt)/86400)` direto no Postgres.
